# 换图泛化测试（应对赛方地图变体）

> 2026-07-04 建立。赛题硬约束："不得写死 playerId / host / port / 阵营 / 地图（会换地图
> 变体，一切以 start/inquire 下发为准）"。本文给出两套互补的换图泛化检验手段，并记录
> 逆向调试包裁判 exe 得到的换图加载机制。

## TL;DR 怎么测

```bash
# 手段 A：无 exe，快，覆盖最全（含改拓扑/角色/极简图）——推荐日常回归
cd client && python -m unittest tests.test_map_generalization -v

# 手段 B：真实裁判端到端跑变体图对局（需先生成 Unity 变体图）
python tools/gen_variant_maps.py
python tools/run_match.py --map tools/variant_maps/unity_reweight.json \
    --client-cmd "python client/main.py {player_id} {host} {port}" --no-ui
# 看 refs/debug-kit-v1/arena/server/data.csv：我方 progress 应 100.00%
```

## 结论（客户端泛化性）

- **源码零硬编码节点**：`client/lychee` 全量扫描无写死 `S01..S15`（命中项全在注释里）。
  终点/宫门/起点一律走 `state.roles.{terminalNodeIds,gateNodeId,startNodeId}`，缺失时
  回退 `node.is_terminal / is_start`；守卡防御值/咽喉判定按 `node_type`（KEY_PASS/GATE/
  PASS）不按 ID；路线选择由 `pathing` 成本模型（帧数+鲜度）动态决定，无"水路是主线"式假设。
- **手段 A 实测**：8 张结构迥异的变体图上，真实策略栈全部合法送达、零非法动作。
- **手段 B 实测**：真实裁判加载"边权翻转"变体图，我方客户端 **479 分 100% 交付**（自动改走
  被调贵后仍最优的线路），而写死路线的官方 demo 在同图 **0% 交付 30 分**——泛化优势的直接证据。

## 逆向发现：裁判怎么换图（调试包 exe）

裁判 `lychee-arena-server.exe` 是 GraalVM native-image 编译的 Spring Boot + fastjson 应用。
逐条实证（探针见 git 历史）：

| 机制 | 结论 |
|---|---|
| `GAME_MAP_PATH` 环境变量 | **有效**，指定外部地图文件路径（`game.map.path` 属性；JVM 认正斜杠绝对路径） |
| 外部图=普通 `map_config.json` / `GameStartMap` 格式 | **失败** `default constructor not found. class GameStartMap`——走 `readJsonMap`(fastjson) 撞 native-image 反射墙 |
| 外部图=**Unity 格式**（含 `grid/legend/assetMapping/unity*Mapping`） | **成功**，走 `readUnityMapConfig` 绕过反射墙，对局正常跑完出分 |
| 文件系统放 `maps/map_config.json` 覆盖内置图（不设 GAME_MAP_PATH） | **无效**，内置图烧死在 classpath/native-image 里 |
| 内置图 | `classpath:maps/map_config.json`，audit 记 `mapConfigFile=map_config.json`；exe 另引用 `maps/map_config_variant_a/b/c.json`（赛方换图占位，调试包未附） |
| routePaths 校验 | 裁判校验 `routePaths[].edgeId` 引用的边存在（"Map routePath references unknown edge"）→ 改边集须同步改 routePaths |

**检测换图是否生效**：看 `server/log.txt` 的 `MATCH_START_SUMMARY` 审计行里 `mapConfigFile`
字段——加载外部图时为你的文件名，否则为内置 `map_config.json`。

> 注意：这是**调试包** exe 的行为。赛方正式服务器用 `variant_a/b/c` 换图（它自己能加载其
> 内部格式）。我们无法确知正式服务器的输入格式，故**客户端泛化性以手段 A（无 exe，直接喂
> 变体 start 消息）为准**，手段 B 是"至少调试裁判能加载的 Unity 格式"上的端到端佐证。

## 手段 A：无 exe 客户端 harness

调试包 exe 无法加载任意外部图（非 Unity 格式撞反射墙），且真正需要泛化的是**客户端**——它
通过 start 消息收地图。故直接用真实策略栈（与 `main.py` 同装配 `[Combat, Delivery, Economy]`）
在变体 start 消息上端到端跑完整局。

- `client/tests/variant_maps.py`——从真实 `start消息.json` 派生 8 张变体（start 消息格式）：

  | 变体 | 变换 | 证伪的泛化风险 |
  |---|---|---|
  | identity | 基线原图 | 保真锚点（客户端本应正常交付） |
  | coords | 坐标全重排 | 任何坐标几何依赖（应只用图上距离） |
  | reweight | 边权翻转 | "某条线是主线"硬编码（路线应成本驱动） |
  | resources | 资源/任务改点 | "冰鉴在 S03"式固定位置假设 |
  | topology | 插新节点 S16 + 新捷径 | 固定 15 节点数、固定连通结构 |
  | roles | 宫门 S14→S15、终点 S15→S16 | 写死 S14=宫门/S15=终点 |
  | minimal | 8 节点极简全 ROAD 链 | 地图缺 KEY_PASS/障碍/多资源时的健壮性 |
  | stress | 上述全维叠加 | 综合 |

- `client/tests/mini_arena.py`——极简本地竞技场：逐帧驱动真实策略栈，本地建模移动/固定处理/
  宫门验核/交付/资源领取，对手停在起点不动。**保真锚点**：先在 identity 上验证客户端能正常
  交付，成立才说明模拟器保真度足够。刻意简化项见文件 docstring。
- `client/tests/test_map_generalization.py`——判据：①保真锚点交付；②每个变体都交付、零非法
  动作（不引用不存在节点、不 MOVE 到非相邻节点）；③解析/寻路/角色派生对所有变体成立。

## 手段 B：真实裁判端到端

- `tools/gen_variant_maps.py`——以 `tools/variant_maps/server_embedded_variant_1.json`（从 exe
  抠出的 Unity 内置图）为模板，做**不改边集**的变换（`reweight` 改距离 / `resources` 改点 /
  `coords` 改坐标并同步 routePath 点 / `combo` 三合一），保证 routePaths 恒有效、对局能跑完。
  输出 `tools/variant_maps/unity_*.json`（可随时重建，已 .gitignore）。
- `tools/run_match.py --map <路径>`——经 `GAME_MAP_PATH` 让裁判加载该 Unity 变体图，其余同常规对局。
- **改拓扑/角色/极简**这类会动边集的变体，Unity 路径需同步重建 `grid.data` + `routePaths`
  像素点（工程量大且是调试 exe 专属校验），**统一交给手段 A 覆盖**，不在手段 B 重复。

## 局限与注意

- `tools/variant_maps/server_embedded_variant_{1,2,3}.json` 是从裁判 exe 二进制抠出的 Unity
  内置图（三份为同图的近乎相同快照，仅个别 distance 序列化舍入差异，**非赛方三张不同变体**）。
  `variant_1` 作 Unity 变体生成模板；2/3 冗余可删。**此三文件由本机既有产物提供，非本次新造**。
- 手段 B 依赖调试 exe 的 Unity 加载路径；换正式服务器行为可能不同。真泛化保证以手段 A 为准。
- 新增变体：手段 A 在 `variant_maps.py` 加一个 `v_xxx` 变换并挂进 `VARIANTS`；手段 B 在
  `gen_variant_maps.py` 加不改边集的变换。两者都有 `validate()` 硬校验合法性。
