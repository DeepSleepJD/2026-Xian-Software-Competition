# 《一骑红尘：荔枝争运战》策略分析

> 本文沉淀对本赛题的整体策略、博弈点、算法与地图变体的分析，作为客户端(`python-client/`)持续优化的依据。
> 官方 L1 demo 仅用于打通链路；策略以"最大化最终总分"为目标，而非对齐 demo。

---

## 0. 一句话结论

这游戏约 **80% 的分是"单人最优化"**（交付 + 任务 + 鲜度 + 好果），对抗层（悬赏/设卡/窗口）是更小、高方差的外挂。核心目标函数是：

> **在保证交付、任务基础分≥130 的前提下，最小化总鲜度损耗。**

时间不是约束（帧数极其富余、且被宫门 450 帧封住），**鲜度才是主约束**，且它还是平局裁决键。

---

## 1. 得分规则与边际价值

最终总分 = 6 项正分 − 惩罚，最低 0。

| 分项 | 公式 | 上限 | 关键性质 |
|---|---|---|---|
| 送达基础分 | `min(240, 120+⌊任务基础分×4/3⌋)` | 240 | **只有交付才结算**；任务基础分 90 拉满 |
| 皇榜任务分 | `min(180, 任务基础分+里程碑)` | 180 | 里程碑 <60:0 / 60-89:+15 / 90-109:+35 / 110+:+50 |
| 好果数量分 | `⌊好果/100×180⌋` | 180 | 每 1 好果 ≈ 1.8 分 |
| 鲜度品质分 | `⌊鲜度/100×180⌋` | 180 | 每 1 鲜度 ≈ 1.8 分 |
| 用时分 | `⌊原始用时分 × min(任务基础分,90)/90⌋`，原始=`⌊(600−交付帧)/600×70⌋` | ~70 | **任务=0 则用时分=0** |
| 破关悬赏分 | `min(悬赏原始,80)+20`（原始>0 时） | 100 | 需 PvP/设卡攻坚 |

**惩罚**：普通非法动作前 5 次免，之后每次 −1（封顶 −20）；交付后违规每次 −5（封顶 −30）。业务拒绝（目标占用/资源不足等）不计非法。

**未交付时**：送达/好果/鲜度/用时全 0；任务分 = `min(基础,80)`；悬赏分 = `min(基础,25)`。

### 边际价值排序（策略地基）

1. **交付 = 生死线**：不交付丢 ~670 分。第一优先永远是"保证交付"，**稳健 > 花活**。
2. **任务基础分 0→90**：送达 +120、任务分 +125、解锁用时分 ≈ **+260**；任务几乎全在必经线上，每个 3-6 帧。
3. **任务基础分 90→130**：送达封顶，仅任务分 +55；**>130 收益为 0** → 最优目标 ≈ **130**。
4. **鲜度是主变量**：鲜度分/好果分都 1.8/点，且鲜度跌破 90/80/…/10 每阈值转坏 1 好果 → 管鲜度同时保两项（合计 360）。
5. **用时分是陷阱**：上限 ~70，被任务系数缩放、又被宫门 450 帧封（最早 ~456 交付），实际 ~15-20 分。**绝不为它牺牲鲜度/好果**。
6. **悬赏分 0-100**：唯一"战斗"分，高方差、依赖 PvP。

## 2. 整体策略

### 单人层面：带采集的最短路，约束是鲜度不是时间

- **帧预算极宽松**：真正需 ~460 帧，上限 600，且 450 帧才开宫门 → ~140 帧富余，**时间不是约束**。
- **真正的约束是鲜度**：每帧掉鲜度（官道 0.055 / 水路 0.045 / 山路 0.07 / 支路 0.065；酷暑 ×1.5 全图；暴雨/山雾区域性）。总损耗 ≈ 帧数 × 平均速率。
- 目标函数：**保证交付 + 任务基础分≥130 前提下，最小化鲜度损耗** → 优先水路/官道、避山路、躲天气命中、末段冰鉴/护果令锁鲜度。

### 两个反直觉但关键的点

- **别空等**：每帧都掉鲜度，"提前到宫门干等"是纯亏。~140 帧富余应用来**顺路刷任务/领冰鉴**（把富余帧以高汇率换分），而非发呆。
- **卡鲜度阈值**：交付时把鲜度停在阈值上方（71 而非 69）可少一次好果转坏；冰鉴时机可用于卡阈值。

### 对战层面（仅当对手也 ~700 时登场）

平台判定：都交付比总分；**同分依次比 鲜度→好果→惩罚**。所以：
- **鲜度既是分也是平局裁决键** → 再次强调死磕鲜度。
- 对强敌，差距来自：① 悬赏分（最多 +100）② 阻断对手交付/逼其掉鲜度 ③ 窗口不吃亏。

## 3. 博弈点

地图末段 `…→S11→S12→S13→S14→S15`（宫门/终点段）在基础图上是**唯一漏斗**，PvP 多围绕漏斗展开（注意：中段拓扑随地图变，见 §5）。

| 博弈点 | 机制 | 博弈本质 | 值不值得打 |
|---|---|---|---|
| 窗口争夺(3拍出牌) | 抢同一资源/任务/处理点/宫门/障碍 | 4×4 **零和 RPS 型矩阵博弈**(验牒/抢行/献贡/兵争循环相克)，成本不对称、手牌隐藏 | 对象价值 > 出牌成本才打；否则弃权，改抢无争议替代品 |
| 设卡+攻坚+强制通行 | 漏斗节点设卡挡路 | **投资/阻断博弈**：花好果设卡赌对手损失更多 | ROI 常低（双方时间富余）；除非逼对手掉到鲜度阈值下或阻其交付 |
| 宫门验核 | 一次一人验核，撞上=GATE 窗口/OBJECT_BUSY | **先到先得 + 时序博弈** | 抢先到宫门有实打实先手 |
| 破关悬赏 | 设卡存活 30/60 帧或逼敌攻坚失败 → 生成；落后方攻破得分 | **诱饵博弈**：设卡既阻断也是悬赏诱饵 | 高方差，最多 100，是拉开强敌的少数手段 |
| 任务争抢 | 任务池有限(18活跃/10可领)，候选点共享 | **拥挤博弈** | 通常够两家都上 90+；别为一个任务卷入亏本窗口 |

**博弈观**：对弱敌纯单人碾压；对强敌，胜负在**鲜度(含平局裁决)+悬赏+不在窗口吃亏**三处的边际。

## 4. 算法映射

| 子问题 | 算法 | 说明 |
|---|---|---|
| 带采集路线规划 | 定向越野/带奖 TSP（图仅 15 点） | 可 Held-Karp 级 DP；任务动态刷新→宜用**滚动时域束搜索**，最大化 `Σ任务价值 − λ·鲜度损耗` |
| 鲜度/好果轨迹 | **确定性模拟器 + MPC** | 规则全公开→可精确前向模拟计划的鲜度曲线并算最终分，"枚举计划→模拟→选最优" |
| 天气 | 有限不确定性规划 | 4 次(窗口 80-120/200-240/320-360/440-480)，提前 30 帧预告；反应式或"天气窗口临近且类型未知时避山/水路" |
| 窗口出牌 | 4×4 零和矩阵博弈求混合策略 Nash(LP) | 按可负担手牌加权；或"期望胜率−成本"启发式，不值就弃权 |
| 设卡/攻坚 | 投资/最优停止 + 阈值启发式 | 估 `阻断收益+悬赏−成本` 期望点差；ROI 低故低优先 |
| 对手建模 | 路线预测(必过漏斗) | 卡宫门时序、择机设卡 |
| 稳健护栏 | 硬规则 | 永不拿交付冒险；障碍用无窗口的强制通行；限非法动作次数 |

**推荐架构**：核心 = 确定性规则模拟器 + 滚动时域路线规划器（交付兜底、任务→130、最小鲜度损耗、顺路采集）；PvP 作为"便宜且正收益才触发"的外挂模块；稳健第一。

## 5. 地图变体：什么固定、什么变、我们如何应对

**晋级过程会换不同地图变体**，开局确定、局内固定。区分固定/可变是保证客户端跨图不崩、不写死的前提。

### 5.1 固定项（可作为常量/假设）

- **核心角色节点(坐标固定)**：起点 `S01(5,50)`、宫门 `S14(76,18)`、终点 `S15(78,18)`。
- 节点编号集合 `S01–S15`（不新增）；站点编号/编码/名/类型/图标固定。
- 路线类型枚举：`ROAD / WATER / MOUNTAIN / BRANCH`（及其耗时系数、鲜度速率固定）。
- 处理机制、资源效果、任务模板(分值/处理帧数)、天气规则(类型/4 次/窗口/时长) —— **规则**固定。

### 5.2 可变项（必须每局从消息动态读取）

- **路线边清单**：边数量、端点、路线类型、是否单向、**路线距离** —— 逐图不同。
- **站点坐标 `S02–S13`** 可变（`S01/S14/S15` 不变）。
- **处理点绑定**：哪些站点要处理、处理类型、处理帧数、是否可能触发窗口。
- **资源投放清单**：哪些站点有哪些资源、数量、领取帧数。
- **任务候选点**：任务能刷在哪些站点。
- **道路障碍候选点**：障碍可能出现在哪些站点。
- 地图格子/天气作用区域（以每帧公开状态为准）。

### 5.3 我们客户端如何做到"地图无关"（现状 ✅）

代码**不写死任何可变项**，全部从 `start`/`inquire` 动态读取：

| 数据 | 来源 | 代码位置 |
|---|---|---|
| 起点/宫门/终点 | `start.map.gameplay.roles.{startNodeId,gateNodeId,terminalNodeIds}` | `strategy.ingest_start` |
| 图拓扑(边/类型/距离/单向) | `start.edges` / `inquire.edges` | `graph.load_edges` |
| 固定处理点(哪些/类型/帧数) | `start.map.gameplay.processNodes` | `graph.load_process_nodes` |
| 任务(实例/目标点/分值/过期) | `inquire.tasks[]` | `strategy._claimable_task_here` |
| 资源库存 | `inquire.nodes[].resourceStock` | `strategy._should_claim_ice` |
| 障碍 | `inquire.nodes[].hasObstacle` | `strategy._advance` |
| 阶段(NORMAL/RUSH) | `inquire.phase`（服务端判定，不自算） | `strategy.decide` |

写死的仅有**规则固定项**：路线类型的耗时系数/鲜度速率(`graph.ROUTE_*`)、资源类型名(`ICE_BOX/HORSE_KEYS`)、天气区域映射(`analyze.WEATHER_HITS`)。`strategy` 里出现的 `S01/S14/S15` 只是默认兜底，且恰好等于固定角色节点，`ingest_start` 会用 `roles` 覆盖。

> 结论：**换图不需要改代码**。路由是对当前图跑鲜度加权 Dijkstra，采集是对当前 `tasks[]/resourceStock` 反应式领取。

### 5.4 尚未充分利用地图信息的地方（改进点，注意）

1. **规划器是"反应式"而非"地图感知"**：只在当前所在节点顺手领任务/资源，不会朝"本图任务/资源密集区"主动规划路线。若某图高价值任务偏离最小鲜度路径，会漏拿。
   → 改进：用 `inquire.tasks[].nodeId` 做**带奖路线规划**（滚动时域束搜索），把"去哪拿任务/冰鉴"纳入路由目标。
2. **冰鉴等资源同理**：现在仅"路线恰好经过才领"。基础图我们的水路不经过冰鉴点，故鲜度提升潜伏未生效；换图路过时才生效。是否**为冰鉴微绕路**应由"收益(鲜度分) vs 绕路(鲜度/帧)"决定——需模拟器支撑，勿盲改（参见 CLEAR 教训）。
3. **单向边**：`load_edges` 已按 `bidirectional` 处理方向；若某图大量单向边导致最短路变化，逻辑自动适配，但需实测验证无死路。
4. **漏斗假设**：§3 的"末段唯一漏斗"是基础图特征；换图中段拓扑会变，PvP 卡位点需按当前图的实际割点重新识别（可对当前图算割点/最小割）。
5. **文中一切具体站点举例**（如"S03/S06/S07 有冰鉴"、"水路 S02→S04→S05→S09"）**仅对当前基础图成立**，不可写入逻辑。

## 6. 当前实现定位与后续

**已覆盖**：交付兜底、任务基础分→180、鲜度加权路由、障碍稳健(强制通行,不用会触发窗口死循环的 CLEAR)、地图无关读取、L1/L2/L3 复盘工具(`analyze.py`)。多种子实测 ~731–742 vs demo ~496，0 惩罚。

**带奖路点规划（已实现）**：每帧评估"绕去拿某个可领任务/冰鉴"是否净收益为正（`增益 − 绕路鲜度×1.8`，任务未到 90 时按 ×2.5 加权因其解锁送达/用时分），是就先去该路点、否则直奔宫门。用富余帧（交付 ~490 vs 上限 600）把"少掉的鲜度"换成任务分和冰鉴保鲜。实测据此自动从水路改走含冰鉴/任务的官道：鲜度分 131→**164–166**、总分 742→**772–774**（对两份真实对手复盘的失分——任务不足、鲜度偏低——均已补上）。

**仍与理论单人最优的差距**：
- 卡鲜度阈值（交付停在阈值上方少一次好果转坏）、路点权重 λ 的精细调参——宜用模拟器验证。

**完全未碰的上限**：PvP（悬赏最多 +100、设卡阻断、窗口出牌）——对弱敌不需要，对强敌是后续上限。

**下一步优先级建议**：
1. 搭**确定性得分/鲜度模拟器**作为离线评估底座（让"改进→验证"闭环，避免 CLEAR 式盲改）。
2. 规划器从贪心升级为**地图感知的滚动时域带奖规划**（任务/冰鉴纳入路由，消灭空等）。
3. 视对手强度再决定是否上 PvP 模块（窗口矩阵博弈 → 悬赏/设卡）。
